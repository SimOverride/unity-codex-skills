# 工作流优化建议

本文件提供跨项目的可选实践。它不是额外的全局约束，不要求每项任务依次执行所有步骤，也不自动授权派发 Agent、合并、发布或清理文件。

## 用明确的交付边界拆任务

按可独立验收的行为拆分，例如“商店刷新规则”“商品列表显示”“接入并验证购买流程”。仅按“UI”“战中”命名容易产生交叉修改。多个任务都需要编辑同一宿主文件时，指定一个集成责任方；暂存区不能作为多人工作的隔离机制。

小修改由一个任务完成即可。复杂模块可采用负责人、实现者、审查者分工，但是否派发以及审批遵循当前用户授权，不为了使用角色模板强行增加 Agent。

## 提示词只补会影响结果的信息

```text
目标：使用者在……时，可以……。
阶段：只分析 / 只预览 / 实现并验证。
范围：本次涉及……；已有设计入口是……。
现状：这些资源有人工修改；当前异常可以通过……复现。
验收：正常情况……；重开/返回……；边界情况……。
允许自行决定：默认值、命名或实现细节……。
```

已有实施 brief 时指向唯一文件，不重复复制全套规范。只澄清影响行为、范围、数据归属或验收的缺项；已经授权的普通实现细节继续处理。

“不流畅”“位置不对”“卡死”可补成可观察条件，例如“开始拖动需要停留一段时间”“首次输入字符时卡住”“第一波敌人出现前合成才发生”。不要把怀疑的原因写成已确认前提。

## 把配置归属与手动操作说明写清楚

配置设计至少回答：谁使用、控制什么、以哪份数据为准、谁会覆盖、何时生效、如何保存。

统一配置入口不等于把全部参数塞进一个文件；表格按使用者工作分组，不按每个类拆一张。保留明确需要独立调整的参数，也避免同一参数在多个位置重复维护。

生成器测试与正式资源维护采用不同约定：验证生成能力时修源或通用生成逻辑；正式资源已人工调整时先确定权威编辑来源，不用旧源文件覆盖。该约定写在对应模块文档，而非复制成所有项目的全局禁令。

## 用最小预览减少完整流程依赖

需要频繁调节动画、界面或组件时，建立能直接启动的局部预览入口，复用正在观察的真实资源与逻辑，用少量数据替代无关系统。

说明预览与运行时在时钟、数据、事件和生命周期上的差异。支持有明确用途的播放、重置和状态选择即可，不默认建设全功能编辑器；保留用户删除或布置的对象，再生成应有明确入口。

## 诊断采用证据更新，而非固定检查表

通用 debug skill 只能帮助发现漏项，无法预先掌握项目语义。复杂问题仍需阅读真实调用者、状态所有者和消费者，选择能够区分假设的观测。

每次只改变能解释结果的关键条件。临时恢复正常不等于根因确认；复发后主动撤回不受支持的判断。编译、静态分析、运行测试和视觉复验分别表述，避免把不同证据等级混在一起。

## 测试对应本次内容

测试提交版本还是工作区版本应明确。隔离测试前后核对待测内容、占用和实际运行结果；工作树 dirty 可以是同步未提交改动后的正常状态。

先复用既有安全脚本。不要为了“干净”清空未知文件，或为了绕过占用不断创建临时项目。只回收本次可证明归属的资源，必要检查通过后不无目的重复全套测试。

## 交接强调当前职责和有效决策

交接应包含职责范围、当前有效设计、代码与文档入口、已完成/未完成、人工改动、Git 状态、验证结果和下一步。不只总结最后一项功能，也不复述整个开发历史。

接收方开始前重新核对磁盘和分支状态，交接摘要只是定位入口。生成交接材料不等于授权创建任务或发送消息。

## 工具开发与正常使用分别计量

区分正常页面/功能工作、工具缺陷修复和工具能力扩展。某个页面遇到问题时，先判断是否为真实通用缺陷，再决定是否改转换器或框架。

评估收益时记录人工纠正轮数、源与生成物往返次数、验证耗时和后续调整难度，不估算未经测量的 token 节省比例。技能只在不同真实任务再次证明有用时增加规则；低频审计先保留短模板。

## 玩法探索按实验验收

先保证移动、交战、伤害和结束条件构成可玩闭环，再每轮验证一个体验假设。指定应保留的已认可特点、此次变化和试玩目标；整合版本不必吸收所有变体机制。

探索任务使用相称的文档和验证，不直接套用完整工程项目的所有步骤。并行变体数量取决于有意义的实验差异与当前授权，不以开满 Agent 为目标。

## 规则存放位置

跨模块长期有效的开发约束进入项目 AGENTS.md；业务行为进入设计文档，代码结构进入开发文档，配置与验证进入使用说明，版本变化进入 CHANGELOG。项目专属类名、资源、概率和测试路径不写入通用技能。

技能需有窄触发条件和结束条件，不因一次小修改强制建图、派发 Agent、全项目审计或补齐无关文档。
