# Unity 模块交付

## 目标

把功能需求交付成当前项目中可运行、可配置、可验证、可维护的实现。以仓库现状和项目规则为准，不套用固定架构。

## 路由

- 需求仍会改变模块边界、数据所有权或核心规则时，先使用 `unity-feature-module-planning`；不要提前编码。
- 根因集中在 Shader、材质、渲染顺序、阴影、透明、模型法线或导入设置时，改用 `unity-render-debug`。
- 任务包含 Blender 模型制作、FBX 结构或动画资产交付时，配合 `blender-unity-asset-pipeline`。
- 用户只要求解释、审查或诊断时，只读分析；除非用户要求修复，否则不要修改。

## 工作流

### 1. 建立项目事实

1. 从当前目录向上和向下确认仓库根、Unity 项目根及 `Assets`、`Packages`、`ProjectSettings`。
2. 完整读取适用的 `AGENTS.md`。检查 Git 状态并保留用户已有改动。
3. 若存在 `.codegraph/`，优先使用 CodeGraph 定位代码；否则使用 `rg`。
4. 查找项目总体文档、模块文档、CHANGELOG、测试程序集和现有相邻模块。
5. 可运行 `scripts/inspect_unity_project.ps1 -Path <目录>` 生成只读项目概况。

需要更完整的检查项时，读取 [references/project-inspection.md](references/project-inspection.md)。

### 2. 理解现有模块

沿真实执行链确认：

- 输入从哪里进入。
- 状态由谁拥有、谁可以修改。
- 配置与运行时状态如何分离。
- 逻辑、表现、UI、存档、网络和资源边界。
- 生命周期、事件订阅、对象池、异步和动画完成时点。
- Prefab、场景对象、项目资源及自动获取组件的来源。

不要只读目标脚本。至少检查调用者、被调用者、数据定义、配置来源、表现入口和测试。

### 3. 处理歧义

只询问会改变以下内容的问题：

- 数据模型或序列化格式。
- 状态所有者或模块职责。
- 玩法结果与事件顺序。
- 生命周期、并发、网络权威或存档兼容。
- Prefab 结构、轴心、场景引用或资源交付。

能从代码、文档、Prefab 或用户既有决定中确认的内容不要再次询问。需求改变时直接删除失效实现，不保留未要求的兼容分支。

### 4. 设计落地点

编码前用简短文字确认：

- 本次负责与不负责的范围。
- 需要修改的状态、配置、API、事件和资源。
- 初始化与事件注册时点。
- 手动配置项和自动获取项。
- 需要迁移或删除的旧逻辑。
- 验收标准。

遵守仓库已有命名、目录、程序集和依赖方向。不要为了“通用”引入当前需求不需要的抽象。

### 5. 实现

1. 先修改稳定的数据结构和纯逻辑，再接表现、UI、资源和编辑器工具。
2. 为代码逻辑添加符合项目语言要求的注释；默认在用户项目中使用中文。
3. 不假设不同 GameObject 或 MonoBehaviour 的 `Awake`、`OnEnable` 顺序。
4. 当前物体或确定父子层级上的组件按项目规则自动获取；外部对象、外部组件和项目资源按项目规则暴露。
5. 事件注册与取消必须对称；异步、Tween、协程和对象池回收必须覆盖中断路径。
6. 保持逻辑状态与动画表现分离，避免动画回调重复修改玩法数据。
7. 编辑器工具、运行时代码、测试和资源配置分别放入现有对应结构。

生命周期与引用检查可读取 [references/lifecycle-and-references.md](references/lifecycle-and-references.md)。

### 6. 维护当前状态文档

按项目规则更新实际受影响的文档，不机械创建空文档。

- 设计文档：目标、功能、规则、职责边界，不写具体实现标识。
- 开发文档：代码结构、数据、依赖、执行流程和验证入口。
- 使用说明：配置、操作、验证和排查。
- 总体文档：更新跨模块关系和当前项目能力。
- CHANGELOG：只记有影响的新增、变化、修复和破坏性调整。
- `AGENTS.md`：只记录以后必须持续遵守的约束性决定。

详细路由读取 [references/documentation-routing.md](references/documentation-routing.md)。

### 7. 验证

按风险选择并实际运行：

1. 编译受影响程序集或解决方案。
2. 运行纯逻辑、EditMode、PlayMode 或集成测试。
3. 检查 Unity Console、Shader 导入和资源重新导入结果。
4. 检查 `git diff --check`、意外生成文件和用户并发修改。
5. 按项目规则检查代码行尾；需要时使用项目格式化工具修正。
6. 若存在 `.codegraph/`，同步更新索引。
7. 对无法自动验证的场景、Prefab、动画和视觉效果给出明确人工步骤。

按任务类型选择验证项时，读取 [references/verification-matrix.md](references/verification-matrix.md)。

### 8. 交付

最终说明：

- 已完成的行为和明确未包含的范围。
- 关键修改位置。
- 需要手动拖拽或配置的字段。
- 自动获取的组件和固定层级要求。
- 已运行的验证及结果。
- 因编辑器占用、缺少资源或缺少真机而未验证的内容。
- 保留的用户原有改动和剩余风险。

不要只报告“编译通过”；交付信息必须让使用者能够配置、复现和验收。
